# Hosted OAuth receiving: domain contract and review

Reviewed October 28, 2026 (America/Los_Angeles; October 29 UTC). **Claim/trade guard implemented and tested in the isolated candidate; Square receiving remains gated.** Source and official documentation were reviewed; fictional-data tests below establish their named subscopes only. No merchant records, credentials, Square writes, installations, production migrations or deployments were used. This work is isolated in `Development/oauth-receiving`.

The agreed direction is a typed, server-owned receiving saga with a central physical-intake claim. Owners and managers may authorize Square writes; buyers and cashiers are denied by default. Receiving stays disabled by both server and tenant configuration until the scoped acceptance gates pass. This does not enable checkout redemption or establish Idaho tax treatment.

## Root-approved engineering decisions

All new hosted trade acceptance, including cash agreements, must bind a central claim for every tenant. Existing accepted receipts and idempotent recovery remain unchanged; unclaimed legacy drafts show an actionable upgrade requirement. No actual credits are reversed or backfilled.

New trade acceptance, linked additional-delivery overrides and new Square writes require a current owner/manager session with enrolled, current-version MFA proved within 15 minutes. Ordinary claim create/read requires a current owner/manager session. Buyer authority stays denied. These are engineering defaults; they do not determine the store's legal trade terms.

The v1 one-operation-per-claim restriction is accepted: excluded rows are explicitly not received and cannot be sent through an additional-delivery shortcut. Quantity-budgeted continuation is a future typed workflow. Original manifests must be captured before edits; old receipts cannot fabricate them. Receiving and automatic checkout remain disabled until their own acceptance gates pass.

## 1. Central physical-intake claims

A claim is a server-issued UUID representing one physical occurrence, shared by all PCs and locations in the tenant. The physical stack or delivery must have its central reference attached or recorded so another PC can select or scan it. A random ID minted independently on each PC is not physical evidence.

Claims retain the original raw CSV SHA-256 when applicable, plus a server-computed versioned semantic fingerprint of the original normalized **all-source** card identities and quantities. Aggregate identical raw-card identities and sort deterministically; retain individually certified slabs separately. Do not use local row UUIDs or truncated numeric SKU hashes as source-line identity. Retail price, review/inclusion flags, storage bin, title, filename and local receipt IDs are excluded from the physical fingerprint.

The shared pure `intake_manifest.py` contract is implemented and covered by 17 focused tests. Its APIs are `capture_manifest(kind, rows, raw_csv_sha256=...)`, `validate_manifest(value)`, `manifest_digest(value)`, `semantic_fingerprint(value)`, `source_line_id(identity)`, `source_lines(value)` and `normalize_identity(identity)`; invalid evidence raises `ManifestError(ValueError)`. A manifest is `{version:1, kind:csv|manual, raw_csv_sha256:csv_only, rows:[{identity,quantity,source_row?}], sha256}`. `source_lines` returns `{source_line_key,identity,quantity,source_rows:[positions]}` groups.

Canonical JSON uses sorted keys, compact separators, UTF-8 and explicit v1 hash domains. Text uses NFC and outer trimming; case, internal spacing, punctuation, printings, grades and certificates remain exact. There is no NFKC, case folding or alias expansion, so potentially distinct identities are not automatically merged. Required original facts are name, game and kind; a slab additionally requires its original grader, grade, certificate and unit quantity. Unknown fields, control/invisible characters and invented CSV references are rejected. Limits are 1,000 original rows, 100,000 units per row, 1,000,000 units total and 512 KiB canonical manifest; an over-limit capture is a visible hosted limitation and must not truncate or break ordinary local intake.

The ordered manifest hash includes original row order/positions, kind and file hash. The semantic fingerprint ignores order/positions/kind/file hash and groups exact identity plus summed quantity. Source-line keys hash original identity alone. On a reordered re-export that resolves to an existing claim, retain the claim's original ordered manifest; map current original identities by `source_line_key`, never zip one file's row positions against another. A correction/split keeps its captured original key, not a hash of its edited identity.

The desktop must capture the original source manifest before operator corrections. The server assigns stable source-line IDs. A plan links each reviewed/corrected line to that original source-line ID, preserving the correction evidence and quantity limits. Never reconstruct an alleged original manifest silently from a mutable edited receipt. Older CSV receipts lacking it need a verified reimport of the same original file or an explicit migration review; uncertain legacy writes remain on the old path regardless.

Base-occurrence claims deduplicate tenant-wide using raw and semantic evidence, independently of receiving location and browser request keys. Two simultaneous PCs resolving the same source converge on one claim under database uniqueness/locking. Different fingerprints that alias the same existing claim must resolve deterministically or block for review. Conflicting claims must never be merged silently.

A separate, explicit manager/owner action records **additional physical delivery**, links the original claim, requires a reason and attestation, and creates a new server occurrence. Retrying that action reuses its exact key and returns the same occurrence. A new HTTP key, re-export, changed price or changed local receipt ID never bypasses duplicate review. If multiple legitimate occurrences match, the operator selects the correct existing central reference; the service does not guess.

No hash can establish whether two visually identical card stacks are physically different. The manual-intake procedure, central tag/reference and explicit additional-delivery confirmation are part of the acceptance contract. A malicious authorized manager can lie about a new delivery; permissions, duplicate warnings and audit must make that boundary visible rather than claim impossible physical identification.

## 2. Typed API and frozen plan

Agreed receiving routes are `POST /api/receiving/plans`, `POST /api/receiving/plans/<id>/commit`, and tenant-scoped plan/status reads. Claims use `POST /api/intake-claims` with `{request_key,physical_reference,source_manifest,physical_delivery_verified:true}`; the optional linked additional-delivery fields are `additional_delivery_of`, `additional_delivery_confirmed:true`, and a 10-200 character `additional_delivery_reason`. Reads use `GET /api/intake-claims/<uuid>` and `GET /api/intake-claims/requests/<request_key>` (typed `{found,result}`). Requests are session/tenant scoped; a central reference is not an authorization credential.

Claim results identify `physical_intake_id`, `version`, `state`, `physical_reference`, `manifest_hash`, `semantic_hash`, original `source_manifest`, `bound_trade_id`, `additional_delivery_of` and explicit policy flags. Trade draft create/update carries `physical_intake_id`, `physical_manifest_hash` and per-line `source_line_key`; new acceptance requires `claim_reviewed:true`. Multiple drafts may reference one open claim, but one atomic acceptance consumes/binds it. A consumed claim is never released by draft void or soft deletion.

The normalized plan accepts only these domain facts:

- Stable client request key; central physical-intake reference or typed source-claim request; original source manifest; explicit new-inventory intent; selected location; expected source/plan revision.
- Reviewed source-line bindings, positive whole quantities, full supported game/card/slab/sports identity, integer USD selling cents and explicit zero-price confirmation when needed. Excluded rows remain in source evidence but are not stock adjustments.
- Optional accepted hosted trade UUID. The server derives included identity, quantity and immutable intake values from that tenant's accepted trade. Retail-label price is separate; the request cannot invent or alter the accepted purchase/credit amount.

Tenant, merchant, Square environment, application identity, provider URLs, HTTP methods, OAuth credentials, catalog object IDs, provider keys and final Square payloads are server-owned. Reject unknown fields, including URL/header/raw-Square-payload proxy inputs. The client never receives a Square token. Current HTTP body limits remain bounded; oversized input is rejected explicitly, not truncated.

The server stores the normalized plan and hash, source/claim linkage, actor, chosen location and provider identity before any mutation. Commit includes the returned plan ID, hash, version, stable request key and explicit confirmation. A changed body under the same key conflicts; a changed plan requires a new reviewed draft revision only before any write. The claim can bind only one v1 receiving operation, including after soft deletion or a lost response.

The proposed receiving first slice is bounded to at most 100 resolved targets, one atomic catalog batch and one inventory chunk. Existing **proven managed**, tracked, matching-price variations are the first allowed path and receive additional copies unchanged. New catalog parents remain default-off until an owner-reviewed server tax/catalog template exists and passes preservation tests. Unproven existing catalog identity and a new price under an existing parent remain review-only until preservation/concurrency coverage is implemented. These limitations must be visible; they are not completion of the full price-SKU migration.

With one v1 operation per claim, selected and excluded quantities must be reported separately. Excluded cards are **not received** and must not be disguised as an additional delivery later. Root accepted this explicit v1 restriction; quantity-budgeted continuations on the same claim remain future work. No silent split or permanent-looking "all received" label is permitted.

## 3. Authorization and provider binding

Owners/managers alone create, commit, recover or cancel receiving writes in the initial policy. Buyer receiving authority is an owner decision and is denied until an explicit permission model exists. Cashiers cannot obtain operation payloads through a generic request-status endpoint. Recheck current enabled staff/session authority at each newly admitted external step; a disable/logout stops later steps, while an already-admitted provider call may still finish and must retain its outcome.

Root approved mandatory enrolled, current-version MFA within 15 minutes for new Square writes, all new trade acceptance and additional-delivery overrides. Recheck at each newly admitted sensitive step; expiry pauses further mutations and preserves recovery identity. Ordinary claim create/read does not imply this extra step-up. An unenrolled account must receive an actionable enroll/sign-in message, never be described as having passed MFA. Existing accepted-result recovery is read/replay, not a new issuance requiring fresh proof.

Bind each operation to tenant, Square merchant, configured environment, application ID, location and verified required permissions. The selected location must belong to the authenticated merchant, be active, use the supported currency and have the required availability. Do not choose the first location automatically. Required receiving permissions are `MERCHANT_PROFILE_READ`, `ITEMS_READ`, `ITEMS_WRITE`, `INVENTORY_READ` and `INVENTORY_WRITE`; existing unrelated features may need their existing scopes separately.

Token refresh may replace credentials for the same verified principal; it must not change the operation body or provider key. Merchant/environment/app changes block resume. Re-consent after revocation requires explicit recovery against the same provider identity and original operation, never a new stock request disguised as a fresh receipt. Requested scopes are not granted-scope evidence. Official token-status documentation describes production credentials; Sandbox introspection behavior remains a provider acceptance gate, with no fallback that treats the requested list as verified.

## 4. Catalog and inventory saga

1. Lock/claim the tenant's physical intake and a durable per-seller receiving lane. Validate all identities, quantities, prices, permissions and location. Read the catalog before mutations. SKU collisions, duplicate matches, missing anchors, ambiguous identity, price/location overrides, non-USD or variable pricing fail closed.
2. Preserve existing fields and sibling variations. Do not reprice/delete an existing variation to make the incoming batch fit. Include exact versions and full original objects when a supported update is required. Avoid replacing a parent with an incomplete child list. A later new-price path must create a compatible sibling without altering old stock variants.
3. Persist each exact provider request, UUID key, endpoint enum, fixed API version and `occurred_at` before dispatch. Never store Authorization headers. Save catalog mappings only from verified response objects. The proposed first slice uses one catalog batch; broader multi-batch support must track partial success explicitly.
4. After confirmed catalog resolution, verify the actual target variation, managed identity, effective price/currency and location before inventory. Persist an additive `NONE` to `IN_STOCK` adjustment for each selected target, with stable operation/line references. Do not turn an incoming quantity into a physical stock count that overwrites existing stock.
5. Verify success from the expected provider response/evidence; a current aggregate count alone is not proof that this particular operation was applied. Keep the seller lane and physical claim occupied during uncertainty. Retry only the original saved request/key or reconcile matching provider changes. No automatic compensation, zeroing, deletion or release on a timeout.
6. Return compact typed state and confirmed SKU mappings/quantities. Set desktop "received" only after all selected adjustments are confirmed. Clear stale labels when a resolved sticker SKU changes. A lost final response is recovered by operation ID/key, not by another receipt or re-issued inventory adjustment.

Suggested states are `draft`, `ready`, `catalog_pending`, `catalog_confirmed`, `inventory_pending`, `received`, `needs_review`, `awaiting_reauthorization`, and `cancelled_before_write`. A precise unknown outcome remains pending/review; it is not success, rollback or safe cancellation. Cancel is allowed before writes. After any possibly applied mutation, preserve the claim and exact journal for manager recovery. Externally concurrent Square edits cannot be made atomic with the application's PostgreSQL transaction; detect version/price changes and retain review evidence rather than promise cross-system ACID behavior.

## 5. Desktop and legacy handoff

Persist the exact claim/plan request body and key before the first cloud call, then persist returned central claim and operation IDs before commit. Use the existing local session nonce and generation boundaries: sign-out/store switch aborts the view, old-window responses cannot update another receipt, and signed-out pending details are hidden. A provider outage never falls back to the local Square vault.

New hosted receiving is available only for an explicitly eligible unreceived receipt with no legacy catalog/stock journal. Existing `committing`, `needs_attention`, received or historically mutated receipts keep their old path and keys. A completed local receipt is not a new delivery. Do not auto-delete local Square credentials or journals during migration. Any owner-reviewed import of old receiving history must be separately designed and tested.

Accepted hosted trade and receiving must share one physical claim **before credit acceptance**. Otherwise two local receipt IDs from one file can issue two credits before receiving deduplication intervenes. New unclaimed acceptance is now guarded in the candidate. Existing accepted legacy results are recoverable without invented claims or another issuance; their conversion to new receiving needs migration review. Do not infer a new purchase, customer credit, cash payment or tax qualification from stock receiving.

Privacy export version 2 adds `physical_intakes` and `physical_intake_requests`, trade binding fields/source keys and scoped claim audit. Original claim rows are linked only through a consumed claim's `bound_trade_id` to the current tenant/customer's accepted receipt, not any draft that happens to reference that claim. Unconsumed/competing-draft original claims remain an explicit owner-review scope limitation. Export record/byte limits still reject oversized data honestly; they do not authorize a silently incomplete copy.

## Official sources reviewed

- [Square permissions](https://developer.squareup.com/docs/oauth-api/square-permissions) maps catalog writes to `ITEMS_WRITE` and inventory writes to `INVENTORY_WRITE`.
- [Token status](https://developer.squareup.com/reference/square/o-auth-api/retrieve-token-status) and [introspection guide](https://developer.squareup.com/docs/oauth-api/token-introspection) expose actual scopes and app/merchant identity; their documented credential context is production.
- [Batch catalog upsert](https://developer.squareup.com/reference/square/catalog-api/BatchUpsertCatalogObjects) describes atomicity per batch, full replacement, seller-level update contention and request idempotency. [Catalog update guidance](https://developer.squareup.com/docs/catalog-api/update-catalog-objects) requires preserving full objects and versions.
- [Batch inventory changes](https://developer.squareup.com/reference/square/inventory-api/batch-change-inventory) limits a request to 100 changes. [Adjustment fields](https://developer.squareup.com/reference/square/objects/InventoryAdjustment) provide external references and timestamps; a reference is not documented as a unique deduplication key.
- [Inventory history](https://developer.squareup.com/reference/square/inventory-api/batch-retrieve-inventory-changes) is paginated; consume all relevant pages for reconciliation. [Locations](https://developer.squareup.com/reference/square/locations-api/list-locations) includes inactive locations, so selection requires validation.
- [Idempotency guidance](https://developer.squareup.com/docs/build-basics/common-api-patterns/idempotency) supports replay of the same request/key. Do not invent a perpetual retention guarantee or retry a changed payload under that key.

Expansion of buyer authority (currently denied); receiving location permissions; central manual-tag operating procedure; future partial-intake continuation; handling preexisting unmanaged SKUs; migration of older local receipt/history evidence; actual Sandbox token proof; supported device/format limits; pricing/cost/vendor fields and subscriptions; journal retention/offboarding; and staging/live acceptance authorization. Mandatory fresh enrolled MFA, manager/owner overrides and the v1 exclusion restriction are already engineering decisions, not unanswered permission requests.

Provider calls, fixtures, live device trials and owner decisions are separate evidence. The design matrix must become passing pure, HTTP, real PostgreSQL concurrency, browser and eventually provider/device cases before writes are enabled. Previous security-pilot results do not certify this new receiving work.
